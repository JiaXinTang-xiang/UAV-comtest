# 当前目录与比赛代码对应说明

## 1. 平台和选手代码的关系

题目已经明确官方技术环境：**Ubuntu 22.04 LTS + ROS2 + PX4/ArduPilot SITL + Gazebo**。我们选择 ROS2 Humble、PX4 v1.14.3、Gazebo Classic 11 实现这套要求。

要分清两个问题：

- **文件是谁写的**：PX4、ROS2、Gazebo 等是上游软件；自主任务与规划节点是我们编写的。
- **比赛会给哪些文件**：官方规定平台，不等于承诺给我们当前这些文件名的目录和脚本。正式场景、模板和接口文件以现场资源为准。

备赛可以按“平台已就绪，选手编写场景 Launch、通信、自检、安全、规划与任务代码”训练。当前本地平台安装、下载和修补较多，是搭建训练环境的工作量，不代表比赛必须从零重写这些软件。

## 2. bao 根目录：每项是什么

以下对应当前实际目录。**本轮不删除、不移动这些文件。**

| 文件或目录 | 内容和用途 | 来源/比赛中的角色 |
|---|---|---|
| `比赛/` | 用户提供的要求 PDF、地图 JPG、仿真要求 JPG | 比赛题目参考材料；不是可直接加载的官方 Gazebo 模型包 |
| `PX4-Autopilot/` | 飞控源码、SITL、Gazebo 飞机/传感器插件 | 上游平台依赖，部分文件由我们修改；选手通常调用其控制接口，不重写飞控 |
| `Micro-XRCE-DDS-Agent/` | PX4 与 ROS2 之间的通信代理、下载依赖和安装结果 | 上游通信依赖；本机做过构建配置调整，不是自主规划算法 |
| `third_party/` | Micro-CDR 源码及压缩包 | 上游第三方构建依赖 |
| `px4_msgs_overlay_ws/` | 单独编译匹配 PX4 的消息类型 | 上游消息定义与我们组织的构建工作空间；不是比赛任务逻辑 |
| `uav_competition_ws/` | ROS2 主工作空间 | 我们组织的工程；选手需要掌握的主要业务代码在它的 `src/uav_competition` |
| `scripts/` | 构建、启动、检查、任务开始和故障训练工具 | 我们编写的操作工具；正式启动/检查可复用，故障注入只用于训练 |
| `config/` | 当前只有 `px4-rc.params`，设置测距安装、高度参考和电池消耗 | 我们配置的训练飞控参数，不是 PX4 全部参数或任务航点 |
| `patches/` | 光流 OpenCV 修复补丁 | 我们对上游插件的修补记录，用于当前平台复现 |
| `tools/` | `vm_gui` 低配 GUI 限帧插件 | 我们写的训练性能辅助；不是题目要求编写的导航核心 |
| `docs/` | 功能、迁移、低配、备赛和历史排障记录 | 我们整理的文档；目录和提交格式按赛规适配 |
| `logs/` | 飞行 CSV/JSON、控制台、仿真进程输出 | 运行生成的证据，需对应实际飞行并按赛规归档 |
| `README.md` | 当前工程总入口、启动流程和链接 | 我们编写的使用说明 |
| 根目录 `build/`、`install/`、`log/` | 曾从根目录编译留下的生成物 | 自动生成；当前主工作空间使用自身的 build/install/log，不是要手写的算法 |
| `competition_course.sdf` | 早期场景文件 | 本地早期训练资源；当前入口使用主包内 `worlds/competition_course.world` |
| `quad_hover.py` | 直接调用 Gazebo 关节施力服务的早期实验 | 本地历史练习，不是当前 PX4 Offboard 控制，不作为正式入口 |
| 根目录 `setup.py` | 旧 `quad_control` 包的打包声明 | 本地历史配置；当前用主包自己的 setup.py |
| `micro-xrce-dds-agent.tar.gz` | Agent 下载压缩包 | 下载材料，不是运行中的算法源码入口 |
| `ABORTING`、`LANDING` | 两个空文件 | 历史终端操作遗留；不是飞行状态配置，不参与任务 |
| `.git/` | 工程版本记录 | 开发工具生成；与飞行控制无关 |
| `.gitignore` | 哪些产物不纳入版本管理 | 我们维护的工程配置 |
| `.vscode/` | 编辑器设置 | 本机开发辅助 |

系统中的 ROS2、Gazebo 及库还在 `/opt/ros`、`/usr`，不属于 bao 中的自编算法。PX4 目录中的本地 Git 元数据仍与当前构建有关，不应把所有嵌套 `.git` 随意删除。

## 3. 真正需要选手编写、理解的主包

路径：`uav_competition_ws/src/uav_competition/`。

| 目录/文件 | 谁提供或编写 | 在比赛中做什么 |
|---|---|---|
| `package.xml` | 我们填写，使用 ROS2 标准格式 | 声明包名、依赖和构建方式 |
| `setup.py`、`setup.cfg`、`resource/uav_competition` | ROS2 Python 包的标准骨架，由我们配置 | 安装节点、注册可执行命令、安装 Launch/配置/模型资源 |
| `launch/` | 我们编写 | 用 ROS2 Launch 组合启动节点；后续需要补统一正式入口 |
| `config/mission.yaml` | 我们编写；正式坐标依赛方任务替换 | 起飞点、目标区、着陆点、路线、速度和保护/规划参数 |
| `worlds/competition_course.world` | 我们按题图重建的训练场景 | 当前可用训练沙盘；不能把它标为赛方发放的原始数字孪生文件 |
| `models/iris_training/` | 上游 Iris 模型基础上由我们配置传感器 | 相机光流、水平雷达、测距、独立真值等仿真数据来源 |
| `models/iris/` | 本地资源映射，含指向训练模型和上游网格的链接 | 让 world 中 `model://iris` 加载训练版无人机 |
| `models/training_surface/` | 我们准备的训练光流纹理 | 给向下相机提供真实图像特征 |
| `uav_competition/` | 我们写的业务 Python 模块 | 自检、控制适配、任务、规划与保护的主体 |
| `test/` | 我们写的检查 | 规划可通行性、场景碰撞与动力学保留检查；不替代实际试飞 |
| `.pytest_cache/`、`__pycache__/` | 自动生成 | 测试/解释器缓存，不是提交核心 |

主工作空间 `src/px4_msgs` 还有一份消息定义；当前构建使用单独 overlay 提供消息，再 `--packages-select uav_competition`。它不是第二套任务算法，不应现场同时改两份消息以解决通信问题。

## 4. 五项比赛功能，现在分别怎么写

### 4.1 启动 Launch 与通信

实际已有文件：

- `scripts/run_xrce_agent.sh`：启动 Agent。
- `scripts/run_px4_competition.sh`：构建 PX4，启动 Gazebo 世界、界面和飞控，等待模型 MAVLink 端口。
- `scripts/run_px4_regions.sh`：加载 ROS 环境和工作空间，启动区域任务 Launch。
- `launch/px4_regions.launch.py`：启动下述四个真实业务节点。

```text
px4_offboard          飞控控制与遥测适配
px4_sensor_adapter    传感器转发
preflight_check       自检及持续有效性监控
px4_region_mission    区域任务与规划
```

**现状：已补顶层 `competition.launch.py`。** 它直接管理 Gazebo、PX4、Agent 和业务节点；`start_sim:=false start_agent:=false` 可连接已经启动的平台。旧 shell 入口保留作故障回退。

### 4.2 自检与安全保护

| 文件 | 当前具体工作 |
|---|---|
| `px4_sensor_adapter.py` | 从真实 PX4/Gazebo 数据源转发光流、向下测距、水平雷达，不用固定值冒充传感器 |
| `preflight_check.py` | 校验位姿、速度、IMU、电量、光流、测距、雷达的数值、时间戳更新和数据新鲜度；发布 READY 与报告 |
| `px4_offboard_node.py` | 起飞前检查，飞行中监视自检丢失、飞控/遥测失效、围栏、高度和飞行超时，必要时请求降落 |
| `px4_region_mission.py` | 监视规划走廊、任务超时、雷达断流、极近障碍和持续无路可走 |

选手需要写的是**检查条件、失败原因、状态转换和保护动作**。传感器的底层物理仿真由 Gazebo 插件实现，飞控自身也保留失联保护。

### 4.3 自动起飞与悬停

核心文件：`px4_offboard_node.py`。

当前流程：

```text
WAITING → READY → PRIMING → SET_MODE → ARM → TAKEOFF
                                                ├─ 独立悬停：HOVER → LANDING
                                                └─ 区域巡航：ACTIVE
```

这个节点负责 NED/ENU 转换、起飞原点标定、连续发送 Offboard 心跳、切换模式、发送解锁命令，再逐步提高位置参考到相对起飞基准 2.5 m。

巡航模式进入 ACTIVE 前，要求高度与水平位置连续约 1 秒满足条件。独立悬停模式可保持 5 秒并记录误差；完整巡航仍以实际任务 CSV/JSON 作为证据。

**PX4 负责姿态/位置闭环及电机输出；我们写位置参考和任务监督，不直接给四个桨叶乱加力。** 当前参考有限速，尚需完善加速度和转弯连续性。

### 4.4 多区域规划和避障

| 文件 | 当前具体工作 |
|---|---|
| `config/mission.yaml` | 指定左右路线的区域目标和中转点，区域顺序仍为 2→3→4→5 |
| `path_planner.py` | 从训练 world 读取墙体碰撞盒，按安全距离膨胀，二维 A* 搜索，再做碰撞检查和可见性简化 |
| `px4_region_mission.py` | 逐区域请求规划，发布路径和位置目标，判定到点；雷达发现未知障碍后保持、异步重规划，再继续任务 |
| `px4_offboard_node.py` | 将任务目标转换为 PX4 位置参考，并限制参考移动速度 |

我们提供区域目标，算法计算中间避墙路径，不是只把截图中的所有箭头逐点硬编码。规划器已从场景碰撞几何读取静态 box/cylinder/sphere，并通过 `frames`、`map.bounds` 和 `model_paths` 配置地图；不支持的 mesh、倾斜或未解析 include 会明确报错，现场资源仍需做一次兼容性检查。

已补：场景碰撞几何解析、地图/世界坐标变换、碰撞约束下的转弯圆角与减速、参考加速度限制、实体临时障碍注入和日志证据检查。仍不能把离线检查或一次训练日志说成全局最优或正式评分认证。

### 4.5 靶标降落

核心文件：`px4_region_mission.py` + `px4_offboard_node.py`。

```text
完成 AREA_5
  → LAND_APPROACH：规划到 mission.yaml 中的 landing_target
  → 满足位置/稳定条件后请求降落
  → Offboard 节点发送 PX4 LAND
  → PX4 下降、接地检测并自动上锁
  → 任务确认完成并记录 JSON/CSV
```

目前是**已知靶标坐标降落**，没有图像识别靶心；题目所贴文字没有明确要求视觉识别。后续补官方落点评分坐标、误差统计与对应原始证据。COMPLETE 证明完成与上锁，不自动等于落点精度得满分。

## 6. 框架是不是比赛要求的样子

**是，核心分工已经对应比赛任务；目前是训练工程，还需整理成现场入口。**

```text
平台依赖：Ubuntu / ROS2 / Gazebo / PX4 / 通信库
                    ↓ 提供物理仿真、遥测、控制接口
选手代码：场景 Launch → 通信适配 → 自检与保护
                    → 起飞悬停 → 区域规划/循迹/避障 → 降落确认
                    ↓
提交材料：源码、配置、真实日志、结果说明、EV 录屏
```

我们目前已把选手代码写在主业务包里。比赛不需要选手重新写 PX4、Gazebo 或 DDS，但需要正确调用它们并实现上述任务逻辑。

整理重点不是继续增加一堆新包，而是：

1. 补统一场景 Launch，参数化配置和接口。
2. 清楚区分正式真实模式、低配训练模式和旧 MOCK 练习。
3. 保留现有成功功能，补悬停统计、轨迹平滑和落点评估。
4. 按现场资源更换地图/接口配置，统一归档与短操作手册。

不能把“我们写好的代码”直接标成“赛方会提供的模板”。如果现场允许带入，可以适配后使用；如果要求现场编写，这套工程就是练习依据，需掌握核心文件并计时实现。
