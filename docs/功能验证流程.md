# 模块 C 功能验证流程

本轮先完成功能，精度留到之后。代码已构建；下面新增功能尚未由选手飞行验收，不算测试通过。已有右路线完整任务成功记录为 `logs/flight/region_20261016_184737.json`。180 分钟是比赛作业时限，配置中的 180 秒是我们自行设置的单次飞行任务保护时限。

## 1. 两次完整路线验证

保留 Agent 终端。关闭上一趟的任务节点和仿真（确认已落地上锁后 Ctrl+C）。不要同时运行多个控制节点。

修改代码后的第一次先编译：

```bash
cd /home/jiaxintang/桌面/bao
./scripts/build_and_source.sh
```

终端 A：

```bash
cd /home/jiaxintang/桌面/bao
./scripts/run_px4_competition.sh
```

终端 B，第一次运行右路线：

```bash
cd /home/jiaxintang/桌面/bao
./scripts/run_px4_regions.sh route:=right 2>&1 | tee logs/right_route.log
```

默认 `enable_tests:=false`。安全策略不需要人工开启，它们随正常巡航节点自动运行。

等 `flight WAITING -> READY` 和自检 `READY`，终端 C：

```bash
source /opt/ros/humble/setup.bash
ros2 service call /uav/mission/start std_srvs/srv/Trigger '{}'
```

等待 `flight TAKEOFF -> ACTIVE`，再等待任务完成。一次任务结束后确认飞机已落地上锁，再重新启动仿真和节点进行下一条路线。

## 2. 右路线回归

新增了异步规划和悬停接口，所以先不加故障，确认更新后仍按区域 2→3→4→5 飞完并 `COMPLETE`。

每个区域会有 `PLAN_REQUEST region_transition` 和 `PLAN_READY`。这属于正常区域路径规划，不代表检测到临时障碍。

右路线完成并确认 `COMPLETE`、自动降落和上锁后，重新启动 PX4 仿真与区域节点，第二次运行左路线：

```bash
./scripts/run_px4_regions.sh route:=left 2>&1 | tee logs/left_route.log
```

左路线在训练地图中对应红色路线的镜像世界坐标，顺序仍然是区域 2 → 区域 3 → 区域 4 → 区域 5 → 降落区。它经过训练图的外通道，使用较低速度和 0.35 m 规划净距；正式场景变化后只需调整 `config/mission.yaml`。

## 3. 开发阶段故障注入（非比赛操作）

下面的断流、走廊、越界、超时和临时障碍命令只用于开发人员检查保护逻辑。比赛没有多次故障测试机会，也不需要在现场执行这些命令；安全策略在两次正常路线任务中自动启用。若要开发验证，仍按下面各小节每次重新启动仿真和节点。

### 3.1 传感器断流

在 ACTIVE 时执行：

```bash
cd /home/jiaxintang/桌面/bao
./scripts/run_training_test.sh dropout
```

预期：TEST sensor forwarding paused=True → lidar_timeout 或 sensor_preflight_lost → LANDING → 上锁；任务 FAILED 并记录对应原因。原始 PX4/Gazebo 数据不停止，统一传感器转发停止，验证的是此通信链路中断。不是 Agent 丢失或 Offboard 心跳丢失测试。

落地后可恢复：

```bash
./scripts/run_training_test.sh restore
```

恢复数据不会重新解锁，下一趟重启仿真和任务。

### 3.2 偏离规划走廊

ACTIVE 且 `PLAN_READY` 后：

```bash
./scripts/run_training_test.sh corridor
```

预期：注入监控偏移 1 m → outside_planned_corridor（打印误差和阈值）→ 自动降落上锁，任务 FAILED。

这是监控输入注入，实际位置和控制目标不变，验证走廊判定与降落链路；不等同于实际侧向扰动飞行测试。

### 3.3 越界

ACTIVE 后：

```bash
./scripts/run_training_test.sh geofence
```

预期：TEST geofence monitor x offset 20 m → Protection: geofence → LANDING → FAILED，上锁。

仅围栏监控输入偏移，飞机不实际飞出场地，位姿遥测不改。实际扰动及定位误差情况下的边界效果留待后续验证。

### 3.4 超时

ACTIVE 后：

```bash
./scripts/run_training_test.sh timeout
```

预期：本次任务期限改为 2 秒后到期 → mission_timeout → ABORTING → 降落上锁 → FAILED。使用同一任务期限检查逻辑，不直接伪造 FAILED。

### 3.5 临时障碍与重新规划

单独重开一趟，等 `mission AREA_3 -> AREA_4`，随后 `PLAN_READY`。此时开始往区域 4 走较长的一段。立即在终端 C 执行：

```bash
./scripts/run_training_test.sh obstacle
```

工具将根据当前已发布的航段，在机前约 1.8 m 生成橙色 `0.4×0.4×3 m` 有碰撞障碍。若航段剩余距离不够，工具拒绝生成，不要重复强行执行。生成工具只访问 Gazebo factory，规划器通过实际雷达发现障碍，没有直接读新物体位置。

预期证据：

1. 工具返回 success=True，Gazebo 看见橙色障碍。
2. 任务打印 `PLAN_REQUEST lidar_path_blocked`，先保持当前位置。
3. `obstacle_points` 大于零，随后 `PLAN_READY`；结果 JSON 的 replans 包含新路径。
4. 绕过橙色障碍，继续区域 4、5，靶标降落并 COMPLETE。
5. 若规划无解，必须明确 `no_safe_path` 并降落上锁，不能穿过障碍；这证明无解保护，但不算绕行成功。

清理障碍：

```bash
./scripts/run_training_test.sh remove-obstacle
```

重启仿真也会移除障碍。下一步无解案例可在确认基本绕行有效后再设计，避免一次修改多个条件。

## 8. 左路线配置与验收

入口已支持：

```bash
./scripts/run_px4_regions.sh route:=left
```

左路线目标按红线顺序配置在 `route_profiles.left`，包含起飞后的横移中转点。当前训练世界的外通道较窄，所以左路线使用 0.35 m 规划净距、0.25 m/s 速度，并保持全局边界和雷达保护。先以完整任务日志确认它能起飞、穿越区域 2→3→4→5、到达回收区并上锁；高度和落点精度按后续阶段验收。
